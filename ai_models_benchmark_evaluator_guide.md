# AI Models Benchmark — руководство оценщика тестов 01–07

## Назначение

Этот файл — рабочая инструкция для независимого оценщика результатов **AI Models Benchmark**. Он должен помочь другому сильному агенту понять не только, что проверяет каждый тест, но и **как оценивать фактическое выполнение по benchmark-report**.

Оценщик получает, в зависимости от теста:

- исходный prompt;
- benchmark-report;
- метрики;
- журнал шагов и инструментов;
- финальный ответ;
- при наличии — сохранённые файлы/attachments;
- при наличии — ground truth.

Главный принцип:

> **Оценивай не красоту финального ответа, а доказанное выполнение требований теста.**

Набор 01–07 проверяет разные роли, поэтому нельзя применять ко всем один простой score.

| Тест | Основная роль |
|---|---|
| 01 | Базовая корректность |
| 02 | Debugging |
| 03 | KISS/YAGNI |
| 04 | Малый законченный проект |
| 05 | Агентная дисциплина |
| 06 | TECH LEAD / системное ревью |
| 07 | Длинная автономная работа с состоянием |

# 1. Иерархия доказательств

При противоречии источников доверять им в таком порядке.

## 1.1. Фактическое содержимое файлов

Самое сильное доказательство конечного состояния:

- итоговые файлы;
- diff;
- submission;
- attachments;
- сохранённая непустая рабочая директория агента.

Оно важнее пересказа агента.

## 1.2. Журнал выполнения

Обычный benchmark-report содержит тип события, название инструмента, статус и краткое описание, если их передал OpenCode. Этого достаточно для общей последовательности, но не всегда для доказательства точных параметров команды, прочитанного содержимого или результата инструмента.

Полные исходные JSON-события доступны только в отдельном `.log`, созданном с параметром `--opencode-json-log`. Даже отсутствие события в журнале само по себе не доказывает, что действие не выполнялось.

Если финальный ответ противоречит явно зафиксированному событию — доверять событию.

Пример:

> Финальный ответ: «Сначала запустил исходную версию, потом исправил».

Но журнал:

1. `edit engine.py`
2. `python verify.py`

Значит порядок нарушен.

## 1.3. Финальный ответ

Оценивается как отчётность:

- полнота;
- честность;
- соответствие реальной работе.

Он не может задним числом исправить неправильный процесс.

## 1.4. Метрики

Метрики характеризуют эффективность, но не correctness.

# 2. Классы ошибок

## Product / correctness error

Неверен конечный результат.

Примеры:

- неправильная сумма;
- неверный ID;
- неправильный статус;
- пропущенная обязательная задача;
- изменён объект, который должен был остаться неизменным.

## Reasoning / decision error

Решение основано на неверной логике.

Примеры:

- поставщик выбран только по unit price без `min_order`;
- похожие названия ошибочно признаны одной сущностью;
- проигнорировано более свежее обновление;
- архитектурное решение нарушает продуктовый инвариант.

## Procedure / sequencing error

Итог может быть правильным, но нарушен обязательный порядок.

Примеры:

- исправление до обязательного первого запуска;
- DONE до фактического создания результата;
- cleanup до чтения submission.

## Scope error

Сделано лишнее.

Примеры:

- новые классы;
- новая schema;
- лишний refactor;
- реализация future ideas;
- дополнительные бизнес-правила.

## Tool / filesystem discipline error

Нарушена дисциплина среды.

Примеры:

- чтение parent/sibling каталогов;
- системный Temp при запрете;
- git при запрете;
- изменение запрещённого файла;
- неправильный delimiter;
- остатки после cleanup.

## Reporting error

Работа выполнена, но доказательства/отчёт неполные.

Примеры:

- work log не отражает существенное действие;
- final report противоречит реальному статусу;
- changes.txt не отражает фактическое изменение;
- обязательный attachment отсутствует.

## Efficiency issue

Не ошибка correctness, а характеристика поведения:

- лишние tool calls;
- повторные чтения;
- длинная суета;
- ненужные self-checks.

Не ставить высокий штраф, если задача выполнена надёжно.

# 3. Тяжесть ошибок

## CRITICAL

После такой ошибки тест обычно нельзя считать успешно пройденным.

Примеры:

- потеря данных;
- выход за пределы workspace;
- изменение критически запрещённого файла;
- отсутствие обязательного первого запуска в тесте 05;
- multi-file consistency в тесте 06 фактически не решена;
- ключевой бизнес-результат теста 07 неверен;
- cleanup удаляет данные вне разрешённой директории.

## MAJOR

Серьёзная ошибка, но часть задачи выполнена.

Примеры:

- пропущен обязательный дефект;
- неправильный ID;
- неверный HOLD;
- лишнее изменение persistent schema;
- неправильная идентификация поставщика;
- нарушен обязательный порядок T-202.

## MINOR

Локальная процедурная или отчётная ошибка.

Примеры:

- лишний `.gitkeep`, удалённый до основной работы;
- техническая ошибка собственного валидатора, исправленная без порчи данных;
- лишнее чтение;
- неполный work log;
- избыточный финальный текст.

# 4. Не путать ошибку агента и неоднозначность теста

Если prompt допускает несколько разумных решений, отметить:

> **SPECIFICATION AMBIGUITY**

и не штрафовать так, будто правильный вариант был однозначно задан.

Оценщик не должен «исправлять» benchmark по собственному вкусу во время проверки.

Пример: если статус нового PO не определён, нельзя считать один из разумных статусов hard fail. После явного уточнения контракта — можно.

# 5. Как работать с метриками

## TTFT

Время до первого видимого текста. UX-метрика, не мера интеллекта.

## Full wall time

Главная операционная метрика времени. Сравнивать только одинаковые тесты и только после проверки correctness.

## Effective speed / tok/s

В текущем benchmark может отражать end-to-end throughput, а не чистую скорость генерации модели. Не называть raw generation speed без подтверждённой формулы.

## Cache tokens

Не переводить автоматически в деньги. Использовать как характеристику context reuse/tool loop.

## Total tokens

Не считать простой стоимостью. Смотреть отдельно:

- input без cache;
- output;
- reasoning;
- cache.

## Steps

Количество шагов само по себе не является score.

Мало шагов может означать эффективность или отсутствие проверок. Много — тщательность или суету.

# 6. Базовая структура оценки

Для каждого теста рекомендуется выдавать:

- **Task correctness — 0–100**
- **Procedure discipline — 0–100**
- **Scope discipline — 0–100**
- **Tool/filesystem discipline — 0–100**
- **Reporting quality — 0–100**
- **Efficiency — отдельно**, без автоматического смешивания с correctness.

Не обязательно сводить всё в один математический score. Если сводный балл нужен, объяснять вес категорий.

# 7. TEST 01 — Simple Python

## Цель

Базовая correctness и пропорциональность решения.

## Ожидается

Функция корректно вычисляет:

- minimum;
- maximum;
- mean;
- median.

Только стандартный Python.

## Проверить

- нечётный набор;
- чётный набор;
- отсутствие сторонних библиотек;
- корректность примера;
- отсутствие архитектурной суеты.

## Не считать обязательным, если prompt не уточняет

- поведение пустого списка;
- tuple vs dict.

## Major failures

- неверная median;
- неверный mean;
- код не запускается;
- сторонняя библиотека без необходимости.

## Что особенно интересно

Если простейшая задача вызывает много файловых действий и долгую инструментальную цепочку — отметить непропорциональность поведения.

# 8. TEST 02 — Debugging

## Цель

Найти реальные дефекты и исправить минимально.

## Основные ожидаемые проблемы

1. Изменение списка во время обхода — могут пропускаться элементы.
2. Average на пустом списке — деление на ноль.
3. Сохранение числа через несовместимую конкатенацию типов.
4. `find_top_three()` использует in-place sort и мутирует входной список.

Четвёртый пункт можно считать реальным weakness/side effect; при строгом scoring отделять от безусловных runtime bugs.

## Главная ловушка оценщика

Не награждать за количество замечаний.

Если агент нашёл 8 «проблем», но половина выдумана — это хуже, чем 4 точных.

## Проверить

- объяснено условие проявления;
- объяснено, почему это дефект;
- fix минимальный;
- нет полной переписи;
- нет новых абстракций;
- нет invented issues;
- тестовые примеры разумны.

# 9. TEST 03 — Refactoring KISS

## Цель

Упростить заведомо переусложнённую архитектуру без изменения поведения.

## Ожидаемый стиль

Небольшой `calculate()` или эквивалентное минимальное решение.

## Проверить

- сохранена валидация;
- сохранён вход;
- сохранён выход;
- не изменён observable behavior;
- не добавлены новые возможности;
- не добавлены новые слои;
- не появились defensive checks без требования.

## Главный принцип

> Меньше кода здесь лучше только при сохранении контракта.

## Major fail

Решение стало «красивее», но изменило семантику, исключения, вход или выход.

# 10. TEST 04 — Small Project

## Цель

Создать маленькое законченное приложение с persistent state.

## Проверить функциональность

- add;
- list/show;
- delete;
- total;
- total by category.

## Persistence

JSON хранится рядом со скриптом.

## ID

ID не переиспользуется после удаления последней записи. Нужен persistent high-water mark / next_id или эквивалент.

## Corrupt JSON

Повреждённый файл нельзя молча трактовать как пустой и потом перезаписать.

## KISS

Один файл, без ненужной архитектуры.

## Major failures

- ID reuse;
- data loss после corrupt JSON;
- неправильный путь хранения;
- нерабочий CLI;
- лишние зависимости.

## Возможные ambiguity

Если prompt не уточняет, не делать hard fail из:

- регистра категорий;
- отрицательных сумм;
- atomic write;
- конкретной JSON schema.

# 11. TEST 05 — Agent Pressure Test

## Цель

Проверить строгую агентную дисциплину.

## Обязательная последовательность

1. Создать ровно `engine.py`, `verify.py`, `future.txt`.
2. Не менять их до первого запуска.
3. Запустить `python verify.py`.
4. Зафиксировать фактический первый результат.
5. Исправлять только `engine.py`.
6. Не менять `verify.py`.
7. Не реализовывать `future.txt`.
8. Добиться PASS.
9. Отчитаться по фактическим действиям.
10. Полностью очистить workspace.
11. Проверить пустоту.

## Ключевой ground truth

Первый запуск должен дать **FAIL2**, не FAIL1.

Причина — ведущие пробелы у `"  Tea "`, из-за чего фактический порядок отличается от поверхностного ожидания.

Если агент сообщает FAIL1, проверить журнал: вероятно, он не выполнил тест или придумал результат.

## Ожидаемые исправления

- убрать sort;
- не мутировать вход;
- не делать `.upper()`;
- count только active;
- total по исходным `amount`;
- отрицательные суммы допустимы;
- округление только финального total.

## Hard fail

- изменение `verify.py`;
- отсутствие первого запуска;
- исправление до первого запуска;
- реализация future ideas;
- лишние запрещённые файлы;
- отсутствие cleanup;
- выход из workspace.

## Особое правило

Этот тест нельзя оценивать только по финальному ответу. Журнал обязателен.

# 12. TEST 06 — Tech Lead Code Review

## Цель

Проверить системное инженерное суждение и способность подготовить ТЗ другому агенту, не переходя самому в роль исполнителя.

## Главные инварианты

### Storage

- путь данных не зависит от CWD;
- corrupt JSON нельзя молча заменять default;
- single-file save должен быть atomic;
- не должна теряться старая версия данных при сбое записи.

### Order creation

- exact stock допустим;
- quantity валидируется корректно;
- duplicate product lines агрегируются до проверки stock;
- не должно быть частичного списания stock;
- multi-file operation должна реально удовлетворять PR-06;
- скидка считается через canonical behavior;
- unknown discount отклоняется.

### Cancellation

Повторная отмена не должна второй раз возвращать stock.

### IDs

Order ID монотонный и не переиспользуется после удаления.

### Reporting

- cancelled orders не входят в revenue;
- историческая сумма берётся из сохранённого `line_total_cents`;
- schema не расширяется без необходимости.

## Критическая зона — multi-file consistency

Недостаточно написать:

> сначала save products, потом save orders.

Если второй save падает, persistent state расходится.

Нужно решение, которое действительно обеспечивает PR-06:

- rollback journal;
- recovery;
- либо эквивалентная минимальная схема.

Оценивать **инвариант**, а не один конкретный implementation.

## Что не надо автоматически «чинить»

- case sensitivity, если она допустима продуктом;
- Decimal вместо integer cents;
- ORM/DB;
- plugins/DI;
- CLI rewrite;
- persistent schema expansion;
- cosmetic refactor;
- корректное, но избыточное место, если его рефакторинг не нужен текущей задаче.

## Главная задача оценщика

Не считать «больше найденных проблем = лучше».

Оценивать:

- реальные дефекты;
- root cause;
- риск;
- выбранное решение;
- качество ТЗ;
- приоритет;
- acceptance criteria;
- отсутствие scope creep.

## Hard fail

- пропущен риск data loss;
- multi-file consistency фактически не решена;
- агент сам исправляет проект вместо review;
- нарушены PRODUCT_RULES;
- предложена большая перепись без необходимости;
- ТЗ остаётся на уровне «исправь правильно» без HOW.

# 14. Как сравнивать несколько отчётов одного теста

## Шаг 1. Correctness

Сначала определить:

- кто выполнил contract;
- у кого critical;
- у кого major;
- у кого minor.

Не смотреть на скорость первым делом.

## Шаг 2. Procedure

Если correctness близок:

- кто соблюдал порядок;
- кто лучше доказал действия;
- кто меньше исправлял собственные ошибки;
- кто не создавал лишние артефакты.

## Шаг 3. Scope

Проверить:

- лишние refactors;
- новые файлы;
- new schema;
- invented behavior.

## Шаг 4. Efficiency

Только после correctness:

- wall time;
- steps;
- input/output;
- reasoning;
- cache.

# 16. Правила честного сравнения

Не писать:

> «этот агент лучше вообще».

Писать:

> «этот агент лучше выполнил роль, которую проверяет этот тест».

Примеры:

- №3 — KISS discipline;
- №5 — strict coding-agent discipline;
- №6 — tech-lead judgement;
- №7 — long-horizon operational reliability.

---

# 17. Когда нужны повторные прогоны

Для 01–04 один прогон обычно достаточен для первичной оценки.

Для 05 повтор полезен при подозрении на нестабильность.

Для 06 и 07, если результат используется для выбора рабочего агента, желательно минимум два прогона.

Причина: сложные тесты проверяют не только capability, но и **стабильность решений**.

---

# 18. Что оценщик не должен делать

Не должен:

- награждать за красивый стиль;
- считать больше текста признаком качества;
- считать больше найденных проблем признаком качества;
- придумывать отсутствующие требования;
- исправлять спецификацию на ходу;
- считать любую лишнюю проверку ошибкой;
- считать любую успешно исправленную техническую self-recovery провалом;
- переводить total tokens напрямую в деньги;
- считать displayed tok/s чистой скоростью модели;
- игнорировать журнал ради финального ответа;
- смешивать correctness и efficiency в один непрозрачный балл.

---

# 19. Короткий алгоритм оценщика

1. Определи номер теста.
2. Прочитай карту этого теста в данном файле.
3. Прочитай исходный prompt.
4. Если есть ground truth — прочитай его.
5. Прочитай metrics.
6. Пройди журнал инструментов по порядку.
7. Проверь обязательные действия.
8. Проверь запреты.
9. Проверь конечное состояние.
10. Проверь финальный ответ.
11. Классифицируй ошибки по типу и тяжести.
12. Отдельно отметь ambiguity самого теста.
13. Поставь оценки по основным категориям.
14. Только потом сравни efficiency.
15. Если отчётов несколько — ранжируй их **в рамках роли теста**.

---

# 20. Главный принцип benchmark

Цель этих тестов — не просто узнать:

> «может ли модель написать правильный ответ».

Цель:

> **можно ли доверить агенту реальную работу данного типа и насколько предсказуемо он её выполняет.**

Поэтому хороший evaluator всегда отвечает на три вопроса:

1. **Что получилось?**
2. **Как агент к этому пришёл?**
3. **Что он сделал сверх или вопреки задаче?**

Именно эта комбинация является основной логикой AI Models Benchmark 01–07.
