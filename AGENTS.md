# Правила работы агента

- Выполняй только явно поставленную задачу и не меняй несвязанные файлы.
- Следуй KISS и YAGNI: выбирай самое простое достаточное решение.
- Не добавляй функциональность, абстракции, зависимости и проверки «на будущее».
- Перед исправлением найди фактическую причину проблемы.
- Не меняй архитектуру, публичное поведение и форматы данных без необходимости или явного согласования.
- Сохраняй существующие пользовательские изменения и не перезаписывай их.
- После изменений выполняй только необходимые проверки и честно сообщай их результат.
- Не создавай новые файлы, если задача этого не требует.

## Документация

- `ai_models_benchmark_changelog.md` - история версий и существенных изменений программы. Дополняй его при добавлении или удалении функциональности, изменении поведения, интерфейса, форматов данных или важных технических решений.
- `ai_models_benchmark_info.md` - актуальная информация о назначении, возможностях, запуске, требованиях и ограничениях программы. Обновляй его, когда меняется текущее использование программы.
- `ai_models_benchmark_todo.md` - список актуальных нерешённых улучшений и вопросов, а не история работы.
- После существенного изменения кода проверь, нужно ли обновить changelog и info. Пиши только относящиеся к изменению сведения, кратко и без дублирования.
- После изменения кода проверь, закрывает ли оно пункт TODO: выполненный пункт удали или уточни; новую запись добавляй только для согласованной отложенной задачи или подтверждённой проблемы.

## Git

- Не выполняй `git add`, `git commit`, `git commit --amend`, создание тегов и `git push` без явной команды пользователя зафиксировать изменения в Git.
- Просмотр `git status`, `git diff` и `git log` разрешён.
- Перед `git add` изучи изменения и определи точный состав коммита.
- Для коммита указывай короткое название с главным смыслом изменения и краткое описание выполненных действий.
- Описание разделяй на относящиеся к коммиту пункты: что добавлено, изменено, исправлено или удалено. Неиспользуемые пункты не пиши.
- Если меняется номер версии программы, сообщение коммита должно начинаться с нового номера в точном формате проекта, например: `v0.9b: описание изменений`.
- По команде `коммит` или аналогичной сначала покажи предлагаемое сообщение и состав изменений, затем дождись подтверждения.
- После показа предлагаемого коммита просьбы изменить, перевести или уточнить его сообщение считаются только редактированием предложения и не разрешают фиксацию.
- Выполняй `git add` и `git commit` только после отдельного однозначного подтверждения: `подтверждаю коммит`, `фиксируй` или `выполняй коммит`.
- Исключение: если пользователь сразу явно просит сделать коммит без предварительного согласования, самостоятельно выбери сообщение и выполни его после проверки изменений.
- При явной команде на коммит включай только изменения текущей задачи; посторонние файлы не добавляй.
